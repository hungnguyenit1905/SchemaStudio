---
title: Data Transfer
description: Copy tables, indexes and foreign keys from one connection to another of the same database type, without going through a file.
---

Data Transfer copies tables straight from one connection to another. It reads rows from the source
in a stream and writes them to the target in batches, so a table larger than memory still goes
through. Open it from **Tools > Data Transfer…**, or right-click a database in the sidebar and pick
**Data Transfer…** to start with that connection and database already filled in.

<Note>
Both connections have to use the same database type. A MySQL source cannot write to a PostgreSQL
target in this version. The target connection also has to allow writes, so a read-only
[Safe Mode](/features/safe-mode) level blocks the run.
</Note>

## The three steps

1. **Source and target.** Pick a connection, a database, and a schema on each side. The target list
   only shows connections of the same database type, and it refuses a target that points at the
   same database as the source.
2. **Tables.** Pick the tables to copy. The list holds tables only, no views, and shows an estimated
   row count for each one. The target table always keeps the source name.
3. **Mode and options.** Pick how the target is prepared, review the checks, then start.

## Modes

| Mode | What it does at the target |
| ---- | -------------------------- |
| Copy (drop and recreate target) | Drops the table if it exists, recreates it from the source structure, then loads the rows. |
| Empty target then transfer | Empties the existing table and loads the rows into it. The table keeps its own indexes and foreign keys. |

## Options

- **Create target table if it does not exist**: in *Empty target then transfer*, creates a table
  that is missing instead of failing on it. With the option off, a missing table is reported as an
  error and nothing is created behind your back.
- **Use a single transaction**: wraps the row loading of each table in its own transaction, so a
  failure part-way through leaves that table as it was. Statements that create, drop or empty a
  table stay outside it, because most engines commit those on their own.
- **Continue when a table fails**: moves on to the next table instead of stopping the run. The
  report lists every failure at the end.
- **Parallel tables**: copies up to three tables at once, each on its own connections. The number
  is capped by the connection pool, and the extra connections are released when the run ends.
- **Parallel reads inside one table**: splits a large table with a single numeric primary key into
  ranges and reads each range on its own connection. The ranges are worked out to hold the same
  number of rows, so a key with gaps still spreads the work evenly. It only engages past a million
  estimated rows, because working out the ranges costs a scan of the key. UUID, text and composite
  keys stay sequential.

## What runs, and in what order

The transfer checks everything it can before it writes anything: it reads the structure of every
selected table, works out which tables already exist at the target, and, for *Empty target then
transfer*, compares the columns. A target table that is missing a column stops the run before it is
emptied. A table that another table outside the selection still references through a foreign key
stops the run before it is dropped, and names the constraint, unless the target confirms it can
disable foreign key checks (MySQL): there, the table is dropped and recreated and the check becomes
a warning instead, on the same terms as the risk below.

Once the checks pass, the run goes through three passes over the whole selection: create the tables,
load the rows, then add the indexes and foreign keys. The first pass runs with foreign key checks
off, because most engines refuse to empty or drop a table another table points at, and the tables
are prepared in no particular order. The checks go back on as soon as the pass ends. Foreign keys go on last so a child table can
be loaded before its parent, which removes the need to order tables at all. After the rows are in,
sequences are lifted to the largest value in the table, so the first insert after a transfer does
not collide with an existing key.

The last pass runs with foreign key checks off too, so a constraint is added without validating the
rows already in the table. That is what a dump and restore does. It means the target can end up
holding a foreign key its rows violate, but only where the source already violated the same one:
the transfer mirrors the source rather than cleaning it up.

The row pass uses the target's native bulk path when one exists: `COPY` on PostgreSQL, and
`LOAD DATA LOCAL INFILE` on MySQL when the server allows it. The MySQL path is served from memory,
never from a file on disk, and binary columns travel as hex so their bytes are not put through a
charset conversion. Anything else falls back to prepared batches, and so does MySQL when
`local_infile` is off at the server. Batches are sized by the target's own limits, so a single row
that is larger than the limit is sent on its own instead of failing the batch.

An index that sorts a column in descending order keeps that order at the target. MySQL before 8.0
and MariaDB before 10.8 accept the syntax and build an ascending index without saying anything, so
the transfer creates the index ascending there and reports it on the table instead of letting the
difference pass unnoticed.

## When a constraint cannot be created

An index, foreign key or sequence reset that the target rejects does not fail the table and does not
stop the run. The rows are already at the target, so the table is listed as **Done, with warnings**
and the reason shows in the tooltip on its status. Every other constraint on that table, and every
table after it, still runs. This is separate from **Continue when a table fails**, which covers a
table that could not be created or whose rows could not be copied.

## Large tables

A table with a primary key is copied in bounded chunks, each one a keyset read over the key, never
an `OFFSET` scan, so chunk 1000 costs the same as chunk 1. The reader and the writer run ahead of
each other through a buffer that holds a handful of chunks, so memory stays flat no matter how big
the table is. A table without a primary key is read in one sequential pass with a warning that it
cannot resume at chunk level.

Every chunk is committed on its own when **Use a single transaction** is off, and the position of
the last committed chunk is written to a checkpoint file after each commit. If the app quits or the
run fails, the next transfer of the same tables asks whether to resume from that checkpoint or
start over. Chunks committed before the interruption are skipped, and nothing is written twice. The
checkpoint only applies to *Empty target then transfer*; *Copy (drop and recreate target)* always
starts over, because it recreates the table. Stopping a run leaves the checkpoint in place, so the
next launch can pick up where it stopped. A checkpoint is cleared only when the run finishes every
table without a failure.

Deadlocks, lock timeouts and dropped connections are retried a few times with a backoff. A row that
violates a constraint is dropped and logged with its key, instead of failing the whole table, when
**Continue when a table fails** is on. Permission, syntax and missing-table errors fail the run
right away.

## The result report

The report compares the actual `COUNT(*)` of every copied table at the source and the target and
flags a mismatch, instead of trusting the estimated row counts shown in the table picker. It also
says how consistent the reads were: a PostgreSQL run pins one snapshot that every connection reads,
reported as consistent across the whole database. Every other engine has no way to share a snapshot
across connections, so the report says the run is consistent per table only, and a table read on
two connections can see two different points in time.

## What is not carried over

- **Generated columns.** They are computed by the server and reject a written value, so they are
  not created and not written. The wizard warns about them before the run.
- **CHECK constraints, partitioning, and triggers.**
- **Views, materialized views, foreign tables and system tables**, which never appear in the list.

## Stopping a transfer

**Stop** ends the run after the current batch. A statement already running on the server cannot be
interrupted, so a large batch finishes first. An open transaction is rolled back, and the report
shows which tables completed, which failed, and which never ran. A table whose rows had already
landed when you pressed Stop is listed as **Done, with warnings**, because its rows are at the
target but its indexes and foreign keys were never added. What the run already committed stays at
the target and is kept in the checkpoint, so the next transfer of the same tables can resume from
it.
